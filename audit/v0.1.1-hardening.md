# v0.1.1-alpha 安全加固记录

基线：`main @ f5a9c43`（v0.1.0-alpha）
本轮变更属于**安全围栏修复 + 文档收口**，不新增功能、不新增电压档位。

**本轮没有对真机施加任何新的运行时 force**，也**没有**重启、刷写、写分区。手机侧只做了只读检查。

## 1. 已修复的缺陷

### 1.1 probe cleanup ownership 缺陷（最高优先级）

`scripts/device-safe-probe.sh` 在 v0.1.0-alpha 中：

```sh
cleanup() { restore; stop_watchdog; }
restore() {
        printf '0' > "$SHUT_ACT" 2>/dev/null
        printf '0' > "$TERM_ACT" 2>/dev/null
}
```

`restore()` **无条件**写两个 `force_active` 节点，而它被注册为 `EXIT` trap 且在每条退出路径上都会执行。后果：

| 场景 | v0.1.0-alpha 的实际行为 | 应有行为 |
| --- | --- | --- |
| `check` 模式（宣称只读） | 退出时写两个 `force_active` | 零写入 |
| preflight 检测到外部 owner 后拒绝 | 退出时把外部 owner 的 `force_active` 清成 0 | 零写入，绝不触碰 |
| 写 `force_val` 后 readback 失败 | 无法区分自己是否已激活 | 只清理自己激活过的节点 |

其中第二项最严重：模块的核心安全承诺是「不碰不属于自己的 force」，而该缺陷恰好会在这种情况下破坏它。

### 1.2 修复方式

引入显式所有权状态 `OWN_TERM` / `OWN_SHUT`：

- **在 `force_active` 写入成功的那一刻**置位（不等 readback 完成），这样 readback 阶段失败时仍能正确回滚
- `restore()` 仅清除标记为已拥有的节点；未拥有的节点**连 `0` 都不写**
- 设备端 watchdog 读取 probe 自己写下的 owner 记录文件，只清理其中列出的节点
- `check` 模式不启动 watchdog，也不设置任何所有权

回归测试对**整棵 mock 内核面**做指纹比对来断言零写入，而不是只比对那两个节点。

### 1.3 BALANCED 缺少 live DT 验证

v0.1.0-alpha 只在 FULL 上做 device tree pair 验证，BALANCED 直接应用。

现在统一为 `profile_dt_ok()`：

| 档位 | 要求 |
| --- | --- |
| `stock` | 无需 DT 证据（不应用任何 override） |
| `balanced` | 必须存在 `3100 / 3150`（normal 档） |
| `full` | 必须存在 `3000 / 3040`（normal 档） |

`service.sh` 与 `action.sh` 都使用该函数。

### 1.4 full 失效时的降级不安全

v0.1.0-alpha 的 `service.sh`：

```
full pair 不存在 -> 降级为 balanced
```

这是错的：一个档位自己的门禁失败，不能作为「另一个非原厂档位可以安全应用」的证据。

现在：**任何档位验证失败都回到 STOCK。**

```
balanced pair 不存在 -> STOCK
full pair 不存在     -> STOCK
```

`action.sh` 输出也改为明确的 `Result: REJECTED / Reason / Fallback: STOCK`。

### 1.5 隐私扫描硬编码构建机用户名

`scripts/privacy-scan.sh` 中的字面量账户名已删除。现在：

- 只使用通用形状（`[A-Za-z]:\Users\...`、`/home/...`、`/c/Users/...`）
- 构建机账户名在运行时从 `${USERNAME:-${USER}}` 取得
- 命中时**只报告「检测到」**，回显中对账户名做 `[REDACTED]` 替换

### 关于「browser download 会被 mock」的说明

`tests/` 不连接真机、不调用 adb。所有测试通过 `DDRC_*_ROOT` 环境变量把脚本指向临时目录中的 mock 文件树。这些环境变量在真机上不存在，因此对实际部署行为无影响。

mock 的 `status` 文件被排除在「零写入」指纹之外，因为它在 mock 中是**内核的输出面**（真实驱动会在 force 改变时重新生成它），不是 probe 被允许写入的东西。对 `force_val` / `force_active` 的断言始终是逐字节比对。

### 源码核对结论（本轮新增）

对照 OnePlusOSS 公开充电框架源码确认：

1. `force_active` 写入会调用 `votable->callback(...)`；写 0 时**同样**调用 callback（用 effective result），所以恢复是回调驱动的，不是「清一个内存变量」
2. `GAUGE_TERM_VOLTAGE` 的 callback 会经 `oplus_mms_gauge_set_deep_term_volt()` 下发 `OPLUS_IC_FUNC_GAUGE_SET_DEEP_TERM_VOLT`
3. 该 callback 还会改写 FCC / SOH 系数（`oplus_mms_gauge_push_fcc_coeff()` / `push_soh_coeff()`）

因此文档中「本模块不是只修改显示值」现在是有源码依据的表述。

同时明确：公开源码**没有**证明 term 配置会被写入 gauge NVRAM，也**没有**证明不会被写入。本项目不对任何一方下结论。
