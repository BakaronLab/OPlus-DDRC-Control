# v0.1.1-alpha 安全加固记录

基线：`main @ f5a9c43`（v0.1.0-alpha）
本轮变更属于**安全围栏修复 + 文档收口**，不新增功能、不新增电压档位。

**本轮没有对真机施加任何新的运行时 force**，也**没有**重启、刷写、写分区。手机侧只做了只读检查。

## 1. 已修复的缺陷

### 1.1 probe cleanup ownership 缺陷（最高优先级）

`scripts/device-safe-probe.sh` 在 v0.1.0-alpha 中：

```sh
cleanup() { restore; stop_watchdog; }
restore() {
        printf '0' > "$SHUT_ACT" 2>/dev/null
        printf '0' > "$TERM_ACT" 2>/dev/null
}
```

`restore()` **无条件**写两个 `force_active` 节点，而它被注册为 `EXIT` trap 且在每条退出路径上都会执行。后果：

| 场景 | v0.1.0-alpha 的实际行为 | 应有行为 |
| --- | --- | --- |
| `check` 模式（宣称只读） | 退出时写两个 `force_active` | 零写入 |
| preflight 检测到外部 owner 后拒绝 | 退出时把外部 owner 的 `force_active` 清成 0 | 零写入，绝不触碰 |
| 写 `force_val` 后 readback 失败 | 无法区分自己是否已激活 | 只清理自己激活过的节点 |

其中第二项最严重：模块的核心安全承诺是「不碰不属于自己的 force」，而该缺陷恰好会在这种情况下破坏它。

### 1.2 修复方式

引入显式所有权状态 `OWN_TERM` / `OWN_SHUT`：

- **在 `force_active` 写入成功的那一刻**置位（不等 readback 完成），这样 readback 阶段失败时仍能正确回滚
- `restore()` 仅清除标记为已拥有的节点；未拥有的节点**连 `0` 都不写**
- 设备端 watchdog 读取 probe 自己写下的 owner 记录文件，只清理其中列出的节点
- `check` 模式不启动 watchdog，也不设置任何所有权

回归测试对**整棵 mock 内核面**做指纹比对来断言零写入，而不是只比对那两个节点。

### 1.3 BALANCED 缺少 live DT 验证

v0.1.0-alpha 只在 FULL 上做 device tree pair 验证，BALANCED 直接应用。

现在统一为 `profile_dt_ok()`：

| 档位 | 要求 |
| --- | --- |
| `stock` | 无需 DT 证据（不应用任何 override） |
| `balanced` | 必须存在 `3100 / 3150`（normal 档） |
| `full` | 必须存在 `3000 / 3040`（normal 档） |

`service.sh` 与 `action.sh` 都使用该函数。

### 1.4 full 失效时的降级不安全

v0.1.0-alpha 的 `service.sh`：

```
full pair 不存在 -> 降级为 balanced
```

这是错的：一个档位自己的门禁失败，不能作为「另一个非原厂档位可以安全应用」的证据。

现在：**任何档位验证失败都回到 STOCK。**

```
balanced pair 不存在 -> STOCK
full pair 不存在     -> STOCK
```

`action.sh` 输出也改为明确的 `Result: REJECTED / Reason / Fallback: STOCK`。

### 1.5 隐私扫描硬编码构建机用户名

`scripts/privacy-scan.sh` 中的字面量账户名已删除。现在：

- 只使用通用形状（`[A-Za-z]:\Users\...`、`/home/...`、`/c/Users/...`）
- 构建机账户名在运行时从 `${USERNAME:-${USER}}` 取得
- 命中时**只报告「检测到」**，回显中对账户名做 `[REDACTED]` 替换

### 构建产物的三个真实缺陷

**缺陷一：GNU tar 产出的不是 ZIP。** `build.sh` 原先依赖宿主的 `tar`。在 Linux 上 GNU tar 即使带 `-a` 也只按文件后缀决定格式（只有 Windows 自带的 bsdtar 会按后缀选格式），于是产出的是名为 `.zip` 的 uStar 归档，`unzip` 会报 `End-of-central-directory signature not found`。现在优先使用 Info-ZIP `zip(1)`，只有 `tar` 时警告，并在写出后校验前 4 字节必须是 `50 4b 03 04`。

**缺陷二：staging 目录在无法保存权限的文件系统上。** ZIP 按条目记录 Unix 权限位，`zip(1)` 从文件系统读取。构建机的仓库位于 `F:` 盘，Windows 盘符经 9p/DrvFs 挂载后**没有 Unix 权限位**：所有文件一律读作 `0777`，`chmod 755` / `chmod 644` 静默无效。结果是已在 `dist/` 中提交的 ZIP 里，**每个条目都是 `-rwxrwxrwx`** —— 包括 `module.prop`、`config.conf` 和 `skip_mount`。

这个缺陷此前完全没有被发现，因为：

- `chmod` 不报错，构建日志里看不出任何异常
- 归档 magic 校验只看前 4 字节，与权限无关
- CI 只检查条目**名字**，既没看权限也没比对内容

修复分两层：`build.sh` 先探测 staging 目录能否保存权限（新建文件、`chmod 640`、确认读回是 `-rw-r-----`），不能就把 staging 换到 `/tmp` 之类的位置，都做不到时明确警告；`verify-artifact.sh` 再独立断言归档里每个条目的权限必须是 `755`（`*.sh`）或 `644`（其余），不满足就判定失败。

**缺陷三：构建随宿主而变化。** ZIP 记录每个条目的 MS-DOS 修改时间，同样的内容在两次构建之间会产生不同字节。`build.sh` 现在把 staging 内所有条目的时间戳固定为同一个值。

### 关于归档字节：为什么 CI 不比对哈希

修完前三点后，CI 仍然在第 14 步失败 —— 该步断言「重建产物与已提交产物字节相同」。原因是 deflate 的输出依赖本机 `zip(1)` 链接的 zlib，这个差异不在本项目的控制范围内。

结论：**跨主机比字节是一个错误的不变量**，它会让 CI 因为与模块无关的原因变红。改为让 CI 断言真正被依赖的性质，全部由 `verify-artifact.sh` 承担：

1. 文件确实是 ZIP
2. 条目集合恰好是模块载荷，且位于根目录
3. 没有镜像、内核模块、分区目录
4. 每个条目的权限是 `755` / `644`
5. **每个条目的内容与工作区 `module/` 逐字节相同**

第 5 条是让 `dist/` 保持诚实的关键：它证明仓库中的 ZIP 仍然描述着它旁边的源码。哈希仍然发布，CI 仍然先校验已提交产物与其 `SHA256SUMS` 一致（这才是下载者依赖的性质），但不再要求重建产物字节相等。

### CI 校验顺序的修正

CI 原先的顺序是「先构建、再校验 SHA256SUMS」，这只能证明构建自洽 —— 被校验的文件本来就是刚生成的，等于什么都没证明。现在改为：先校验已提交的 `dist/` 产物与 `SHA256SUMS` 一致，再构建，再校验产物不变式，最后确认重建后 `SHA256SUMS` 未变。

### 发布引用一致性检查

`scripts/audit.sh` 新增第 7 节：扫描所有 tracked 文件中出现的 `OPlus-DDRC-Control-*.zip` 引用，任何不是当前 `module.prop` 版本的引用都判为 FAIL；校验 `dist/SHA256SUMS` 列出的文件集合与 `dist/` 中实际存在的 ZIP 完全一致；并调用 `verify-artifact.sh` 校验产物。

加入这条检查的直接原因：本轮发现 README「安装步骤」仍在指引用户下载已被弃用的 `v0.1.0-alpha`。文档指向错误的产物是一种不会触发任何现有检查的失效模式，因此补上了自动化检查。

### 关于「browser download 会被 mock」的说明

`tests/` 不连接真机、不调用 adb。所有测试通过 `DDRC_*_ROOT` 环境变量把脚本指向临时目录中的 mock 文件树。这些环境变量在真机上不存在，因此对实际部署行为无影响。

mock 的 `status` 文件被排除在「零写入」指纹之外，因为它在 mock 中是**内核的输出面**（真实驱动会在 force 改变时重新生成它），不是 probe 被允许写入的东西。对 `force_val` / `force_active` 的断言始终是逐字节比对。

### 源码核对结论（本轮新增）

对照 OnePlusOSS 公开充电框架源码确认：

1. `force_active` 写入会调用 `votable->callback(...)`；写 0 时**同样**调用 callback（用 effective result），所以恢复是回调驱动的，不是「清一个内存变量」
2. `GAUGE_TERM_VOLTAGE` 的 callback 会经 `oplus_mms_gauge_set_deep_term_volt()` 下发 `OPLUS_IC_FUNC_GAUGE_SET_DEEP_TERM_VOLT`
3. 该 callback 还会改写 FCC / SOH 系数（`oplus_mms_gauge_push_fcc_coeff()` / `push_soh_coeff()`）

因此文档中「本模块不是只修改显示值」现在是有源码依据的表述。

同时明确：公开源码**没有**证明 term 配置会被写入 gauge NVRAM，也**没有**证明不会被写入。本项目不对任何一方下结论。

## 5. 回归测试的有效性验证

回归测试本身也必须被验证，否则「测试通过」可能只是因为它什么都没检查。本轮对最高优先级的那条断言做了反向验证。

现有的 `check mode: external owner active -> zero writes` 断言依赖 `assert_zero_writes`：它对整个 mock 内核面（`proc/oplus-votable`、`sys/class/oplus_chg`、DT 树）做指纹快照，指纹包含 **内容、mtime 和 inode**，而不是只比较内容。

反向验证方法：把 v0.1.0-alpha 的缺陷行为临时塞回 `restore()`：

```sh
restore() {
	printf '0' >"$SHUT_ACT" 2>/dev/null
	printf '0' >"$TERM_ACT" 2>/dev/null
	return 0
}
```

预期：该测试必须 FAIL。

实测结果：**FAIL**，且失败信息同时给出两类证据：

- `something under the mock kernel surface was modified` —— 指纹变化
- `expected [1] got [0]` —— 外部 owner 的 `force_active` 被清掉

值得单独说明的是，本次反向验证还确认了指纹比内容比较更强：即使把 `0` 写进一个**本来就已经是 `0`** 的节点，内容不变但 mtime 改变，指纹依然报错。也就是说「重复写入相同值」这种最隐蔽的越权写入也会被抓住。

验证完成后已还原正确的 `restore()`，全量套件重新通过（102 项断言）。
